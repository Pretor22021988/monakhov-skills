# GitOps вместо SSH

Ручной деплой — императивный, ручной, скрытый: что стоит на машине, знает только
тот, кто последним копировал файлы. GitOps — декларативный, через ревью,
воспроизводимый: что стоит на машине, видно в git, а вернуть прошлое состояние —
одна команда.

## Четыре правила

1. **Состояние — в git.** Код, конфиги без секретов, версии зависимостей
   (lock-файл), команда запуска. Всё, что нужно, чтобы поднять систему с нуля.
2. **Версия — это тег.** Деплоится тег (`v5.6`), а не «последний скачанный файл».
   Тег неизменяем, поэтому «что сейчас стоит» имеет однозначный ответ.
3. **Изменение — через коммит с причиной.** В сообщении: что меняется и зачем.
   Для значимых правок — ветка и PR, даже если ревьюер ты сам: дифф перед
   слиянием ловит то, что пропускает «скопировал поверх».
4. **Машину не правят руками.** Ручная правка на месте — дрейф. Деплой сначала
   проверяет, что рабочая копия чистая, и останавливается, если нет.

Секреты в git не кладут: в репозитории `.env.example` с ключами без значений,
`.env` — в `.gitignore`. Если секреты нужно версионировать, — шифрование
(sops + age), а не открытый текст.

## Что выдавать пользователю вместо ручных шагов

Плохо: «скачай файл → скопируй в папку → останови процесс → запусти».
Причины: путаница версий в «Загрузках» (`file (1).py`), нет истории, нет отката,
непонятно, что сейчас работает.

Хорошо — три части:
1. **Изменение как коммит**: патч (`git apply`) или готовые файлы плюс команды
   `git add / commit -m "…" / tag vX.Y / push`. Если пользователь работает только
   в веб-чате без доступа к git — выдай файл и сразу команды, которые положат его
   в репозиторий и поставят тег.
2. **Одна команда деплоя** — `scripts/deploy.sh` из этого навыка (адаптируй пути):
   проверка дрейфа → `git fetch` → переход на тег → проверка → перезапуск → запись
   в журнал деплоев. Не прошла проверка — автоматический откат.
3. **Команда отката**: `deploy.sh <каталог> <предыдущий-тег> …`.

## Pull или push

- **Одна машина, домашний ПК, VPS без Kubernetes** — pull-скрипт `deploy.sh`,
  запускается вручную или планировщиком (cron, Планировщик заданий Windows).
- **Kubernetes** — оператор, который сам тянет состояние из git: Argo CD или Flux.
  Подробности и минимальный манифест — `references/kubernetes.md`.
- **Push из CI** (GitHub Actions по ssh) допустим, но это уже не чистый GitOps:
  CI получает доступ к продакшену. Предпочитай pull, если машина может ходить в git.

## Проверка перед перезапуском

Минимум, который ловит больше всего поломок: синтаксис/компиляция
(`python -m py_compile …`), запуск тестов, если они есть, и проверка версии в коде
(`grep VERSION`). Перезапуск — только после успешной проверки.

## Журнал и откат

`deploy.sh` пишет строку «дата, было → стало, тег» в журнал вне репозитория.
Откат — деплой предыдущего тега; новый коммит для этого не нужен. Если после
отката нужна правка — исправление идёт новым тегом, а не ручной правкой на машине.

## Антипаттерны — называй их, если видишь

- ssh + редактор на продакшене; scp поверх; «поправил на сервере, потом закоммичу»
- деплой «последнего файла из Загрузок» без версии
- `pip install` без зафиксированных версий
- секреты в репозитории
- один общий «prod»-каталог, где нельзя сказать, какой коммит в нём лежит
