# Terraform как система

Один `main.tf` на 300 строк работает, пока его пишет один человек для одного
окружения. Система — когда понятно, где что лежит, окружения не мешают друг
другу, а изменение проходит ревью до того, как тронет инфраструктуру.

## Структура по умолчанию

```
terraform/
  modules/
    network/        main.tf variables.tf outputs.tf versions.tf README.md
    kubernetes/
    database/
  envs/
    dev/            main.tf (вызовы модулей) backend.tf terraform.tfvars
    prod/
```

- **Модуль** делает одну вещь и общается с миром только через `variables.tf`
  (вход) и `outputs.tf` (выход). Внутренние ресурсы снаружи не трогают.
- **Окружение** — тонкий слой: вызывает модули с разными параметрами и хранит
  своё состояние. Различия между dev и prod — в переменных, а не в копиях кода.
- Модуль, который не используется хотя бы в двух местах или не скрывает
  сложность, модулем быть не должен — не дроби ради дробления.

## Состояние (state)

- Только удалённо: S3-совместимое хранилище (AWS S3, Yandex Object Storage и
  подобные) или Terraform Cloud. Локальный `terraform.tfstate` в git — нельзя:
  там бывают секреты, и двое одновременно его ломают.
- Блокировка обязательна: два `apply` одновременно портят состояние. Способ
  блокировки зависит от backend и версии Terraform — сверяй с документацией
  своей версии, а не по памяти.
- Отдельное состояние на окружение. Поломка dev не должна задевать prod.

## Версии

`versions.tf` в каждом модуле и окружении: `required_version` и
`required_providers` с ограничением версии; `.terraform.lock.hcl` — в git.
Без этого один и тот же код через месяц даёт другой план.

Если реестр провайдеров недоступен из сети, используй зеркало провайдеров
(через `provider_installation` в CLI-конфиге) или OpenTofu — проверь
доступность до того, как строить на этом процесс.

## Поток изменения

1. Ветка → `terraform fmt -check` → `terraform validate` → линтер (tflint) и
   проверка безопасности (checkov или trivy config), если есть.
2. `terraform plan -out=plan.bin` — план приложен к PR, ревью читает план,
   а не только код. Особое внимание строкам `must be replaced` и `destroy`.
3. `apply` только этого сохранённого плана, только после слияния и только из
   одного места (CI или выделенный раннер), а не с ноутбуков.

## Рефакторинг монолитного main.tf без пересоздания ресурсов

Переезд ресурса в модуль меняет его адрес, и наивный план предложит удалить
и создать заново (для базы данных это катастрофа).

1. Перенеси код ресурса в модуль, вызови модуль из окружения.
2. Опиши переезд блоком `moved` (Terraform 1.1+):
   ```hcl
   moved {
     from = aws_vpc.main
     to   = module.network.aws_vpc.this
   }
   ```
   Для старых версий — `terraform state mv` (с резервной копией состояния).
3. `terraform plan` должен показать **0 to add, 0 to destroy** — только
   переименования. Любое `destroy` на этом шаге — стоп, ищи пропущенный `moved`.
4. Переноси по одному модулю за PR.

## Чек-лист ревью Terraform-кода

- нет захардкоженных секретов, паролей, ключей; секреты — из хранилища секретов
  или переменных с `sensitive = true`
- у модулей есть `variables.tf` с типами и описаниями, `outputs.tf`
- `prevent_destroy` на ресурсах, потеря которых необратима (базы, бакеты с данными)
- теги/метки владельца и окружения на ресурсах
- нет `count`/`for_each` по спискам, порядок которых может меняться (индексы
  съедут и ресурсы пересоздадутся) — предпочитай `for_each` по map со стабильными ключами

## Как показывать это на собеседовании и в портфолио

Не «знаю Terraform», а «разбил монолит на модули network/k8s/db, окружения
dev/prod с отдельным удалённым состоянием, перенёс без пересоздания ресурсов
через `moved`, план проходит ревью в PR». Цифры — сколько окружений, сколько
времени занимает поднять новое, сколько ручных шагов исчезло — только реальные.
